Base L1 and L2 bridge addresses: the official list

The Base L1 and L2 bridge contract addresses are on Base’s official contracts page: Ethereum’s L1StandardBridge and portal, plus Base’s L2 predeploys.

The Finality DeskNov 27, 2026 · 22:53 UTC4 min read#179fdd

The official Base bridge contract addresses are listed on the Base Contracts page on docs.base.org. For Base mainnet, the key Ethereum contracts are L1StandardBridge and OptimismPortal; on Base, they are L2StandardBridge and L2CrossDomainMessenger.

Use the network-specific addresses when you configure an integration or inspect a transaction. Before you bridge from Ethereum to Base, confirm that the route and token are supported, then compare the displayed contract with the official Base list.

What are the Base L1 and L2 bridge contract addresses?

The Base mainnet bridge addresses are split between Ethereum and Base, and the L1 contracts are specific to Base.

  • Ethereum, L1StandardBridge: 0x3154Cf16ccdb4C6d922629664174b904d80F2C35
  • Ethereum, OptimismPortal: 0x49048044D57e1C92A77f79988d21Fa8fAF74E97e
  • Base, L2StandardBridge: 0x4200000000000000000000000000000000000010
  • Base, L2CrossDomainMessenger: 0x4200000000000000000000000000000000000007

The Base Contracts page groups deployed contracts by network. Use its Ethereum Mainnet and Base Mainnet entries for these addresses; testnet entries belong to separate deployments.

Why are the Base L1 and L2 bridge addresses different across OP Stack chains?

The L2 bridge predeploys use shared OP Stack addresses, while each chain has its own L1 contracts.

On Base, L2StandardBridge and L2CrossDomainMessenger sit at fixed predeploy addresses. OP Stack chains reserve these address slots for system contracts, so the same L2 address can identify the corresponding contract across chains. That shared address does not make the contract a universal bridge endpoint: the Base predeploy is on Base, and an equivalent address on another OP Stack chain is on that chain.

The Ethereum side is chain-specific. Base’s L1StandardBridge and OptimismPortal are deployed for Base’s connection to Ethereum. OP Mainnet has its own L1 deployments and addresses. A developer who copies OP Mainnet’s Ethereum bridge address into a Base integration can call the wrong chain’s contracts, even though the L2 predeploy addresses look familiar.

Keep the chain and side with every address in configuration: Ethereum mainnet plus Base mainnet for a Base deposit, and Base plus Ethereum mainnet for a withdrawal. The Base bridge path depends on the matching L1 and L2 contracts and their cross-domain messaging relationship.

How do I verify a Base bridge contract address?

Compare the full address on Base’s Contracts page with the address displayed on Etherscan or Basescan for the correct network.

Open the address page directly in the relevant explorer and inspect its name tag. The Ethereum L1StandardBridge address should be identified as Base’s bridge, and the Base L2StandardBridge should appear as the L2 Standard Bridge proxy. Verify all 40 hexadecimal characters; a matching name or similar-looking address is not enough.

These contracts are proxies. The proxy address is the stable endpoint used by integrations, while its implementation can be upgraded. An explorer may show both the proxy and its current implementation address. For an integration, use the documented proxy address. For a code-level review, inspect the verified proxy and implementation information on the explorer alongside the official Base entry.

Can I send ERC-20 tokens to the bridge address directly?

No: a plain ERC-20 transfer to a bridge contract does not perform a deposit and can leave the tokens stuck.

A standard ERC-20 deposit uses the bridge’s deposit function, such as depositERC20 or depositERC20To, with the token addresses and other required parameters. The ERC-20 approval and deposit call are distinct steps: approval lets the bridge spend tokens, and the deposit function initiates the cross-chain action. A direct transfer only moves tokens to the contract; it does not supply the deposit instructions or start the bridge message.

Use a supported bridge interface or implement the documented deposit flow against the correct L1StandardBridge. Confirm the L1 token and its intended L2 representation before submitting. Do not treat the published address as a general-purpose wallet or token destination.

Where are the Base Sepolia testnet bridge contract addresses?

Base Sepolia addresses are listed separately on the Base Contracts page under the testnet sections, and they must not be substituted for the mainnet addresses above.

For testing, match both sides to the test networks: Ethereum Sepolia for L1 and Base Sepolia for L2. An address may resemble a mainnet predeploy address while referring to a testnet deployment. Keep testnet and mainnet settings separate in scripts and wallet configuration.

What is the native USDC contract address on Base?

The native USDC address on Base is a token contract address, not one of the bridge contracts listed above.

Use Circle’s official USDC contract-address information to identify the current native token address for Base, then verify the token’s name and symbol on Basescan before using it. Do not infer a token address from the L2StandardBridge or assume that every asset labeled USDC is native USDC; bridged versions can have different contract addresses.
